# Build the pure core first, then simulate it

For a greenfield workspace that injects all entropy, the best route is the one Firezone and Polar Signals took. Write each component as a sans-IO state machine whose inputs are `handle_*(…, now)` and whose outputs are drained with `poll_*`. Drive many such machines from one seed in a single-threaded harness. Check the result against a small executable reference model using proptest-state-machine, and later feed the same harness to a coverage-guided fuzzer. The most valuable reading is short. Thomas Eizinger's Firezone post "sans-IO: The secret to effective Rust for network services" (2024) and its sequel "Finding bugs you didn't think to test for" (2026) cover the design and the payoff. Polar Signals' "Theater of State Machines" (2025) gives the minimal DST architecture in Rust. The ShardStore SOSP 2021 paper shows how to write reference models and operation alphabets. The sled simulation guide and Phil Eaton's overview cover the theory. The best code to read is quinn-proto and str0m for core API shape, Firezone's `rust/tests/fuzz/src/` for the harness, Turso's `testing/simulator` for workloads, properties and shrinking, and Neon's `libs/desim` for a compact discrete-event simulator. Runtime-replacement tools (madsim, turmoil, mad-turmoil) are mainly for retrofitting existing tokio code. They are worth understanding but are not piton's main path. One local conflict needs a decision early. Both S2 and Firezone use `debug_assert!` for invariant checks, and piton's lints ban it, so piton needs another mechanism, such as plain `assert!` or a sim-only feature.

## Five readings carry most of the weight for a pure-core design

Most of the material splits into three threads: the sans-IO API pattern, DST architecture, and stateful property testing. The best sources join all three. The **Firezone sans-IO post (July 2024)** is the canonical Rust writeup. It treats sans-IO as dependency inversion: a send becomes a `Transmit` value instead of a socket call. Every function that needs time "receives an `Instant` parameter instead of calling `Instant::now` itself". The post also argues that a state machine needs only `&mut self`: no `Arc<Mutex<T>>`, channels or `'static` spawned futures ([Firezone](https://www.firezone.dev/blog/sans-io)). The **2026 sequel** shows the payoff. Clients, gateways and relays run in a simulated network, driven by generated `Transition`s against a `ReferenceState`. **About 500 replayed scenarios reach over 85% coverage in under 2 minutes**, and a nightly 30-minute fuzz job has a bot open PRs that add corpus inputs ([Firezone 2026](https://www.firezone.dev/blog/finding-bugs-you-didnt-think-to-test-for)). **Polar Signals' post** reduces DST to one trait: `receive(&mut self, m) -> Option<Vec<(Message, Destination)>>` and `tick(&mut self, now)`. A single-threaded message bus is the only scheduler and the only place faults are injected, and one printed seed drives everything ([Polar Signals](https://blog.polarsignals.com/blog/posts/2025/07/08/dst-rust)). The **ShardStore paper** is the industrial template for the model side. Its reference models are executable Rust at about **1% of implementation size**. Its operation alphabets include background operations that are no-ops in the model. The approach **prevented 16 issues from reaching production**, and checking code was about 12–13% of the codebase ([Bornholt et al., SOSP 2021](https://jamesbornholt.com/papers/shardstore-sosp21.pdf)).

## Sans-IO cores converge on one handle/poll vocabulary

The Rust exemplars share an API. Inputs arrive through `handle_*` methods that take the current `Instant`. Outputs are drained through `poll_transmit`, `poll_event` and `poll_timeout`. The caller owns sockets, clocks and buffers. Two contracts recur: **drain all outputs after every input**, and **time is monotonic and supplied by the caller**. quinn-proto states its contract most precisely. Events and timeouts at the same instant may interleave in any order, the recommended polling order is transmit, timeout, endpoint events, app events, and `poll_timeout` must follow `poll_transmit` ([docs.rs Connection](https://docs.rs/quinn-proto/latest/quinn_proto/struct.Connection.html)). str0m takes the other style. A single `poll_output()` enum is drained until `Output::Timeout`, and the docs warn that mutating twice without draining leaves the engine inconsistent ([docs.rs str0m](https://docs.rs/str0m)). For piton, the single-enum style is the safer default: it makes "drain until Timeout" one loop the harness cannot skip.

|---|---|---|

Firezone's own warnings are the most useful guide to design risk. A hand-written event loop busy-loops if `poll_timeout` is not advanced. Sequential workflows need more code than `async`. Dependencies must themselves be sans-IO or written in-house. The IO shell still needs Docker end-to-end tests ([Firezone](https://www.firezone.dev/blog/sans-io); [Firezone 2026](https://www.firezone.dev/blog/finding-bugs-you-didnt-think-to-test-for)). James Munns's critique applies to piton too. Explicit enum states cause nested matches, borrow-checker friction and placeholder values, while async handles timeouts, racing and cancellation well ([SDR](https://sdr-podcast.com/episodes/sans-io/)). The reasonable line is to use sans-IO for long-lived controllers with timers, many peers and failure cases, and to accept plainer code for sequential glue in the shell. The experimental `asansio` crate, which generates sans-IO machines from async/await, hints at a future middle ground ([docs.rs](https://docs.rs/asansio/latest/asansio/)).

## Turso, Neon and Firezone show the harness side best

Sans-IO exemplars teach the core. DST exemplars teach the harness: workload generation, fault injection, invariants, shrinking, and checking that the simulation is itself deterministic. **Turso's `testing/simulator`** is the richest public example. It generates random configurations, builds "interaction plans" of SQL plus properties, and has `--seed`, `--doublecheck` (run twice and compare), `--differential` (against SQLite), and a `shrink/` module ([README](https://github.com/tursodatabase/turso/blob/main/testing/simulator/README.md)). Its sibling `testing/concurrent-simulator` ("Whopper") adds yield injection, allocation faults and Jepsen's Elle checker ([README](https://github.com/tursodatabase/turso/blob/main/testing/concurrent-simulator/README.md)). **Neon's `libs/desim`** is a compact discrete-event simulator borrowed from FoundationDB. Its virtual time fast-forwards through idle periods. It is used in `safekeeper/tests/walproposer_sim/` and `random_test.rs` to test a consensus protocol ([desim](https://github.com/neondatabase/neon/tree/main/libs/desim), [walproposer_sim](https://github.com/neondatabase/neon/tree/main/safekeeper/tests/walproposer_sim)).

Three ideas carry across every exemplar, and piton should adopt them from day one. First, **one printed seed** drives scheduling, ticks and faults ([Polar Signals](https://blog.polarsignals.com/blog/posts/2025/07/08/dst-rust)). Second, **an automatic determinism self-check**: Turso's `--doublecheck`, S2's CI job that runs one seed twice and diffs TRACE logs, and Commonware's comparison of `auditor().state()` across runs ([Turso](https://github.com/tursodatabase/turso/blob/main/testing/simulator/README.md); [S2](https://s2.dev/blog/dst); [Commonware](https://docs.rs/crate/commonware-runtime/latest/source/TESTING.md)). Third, **turning a found bug into a regular test**, because a seed stops reproducing a bug once the code changes ([Eaton](https://notes.eatonphil.com/2024-08-20-deterministic-simulation-testing.html)). Correctness checking is also moving from ad-hoc assertions to history checkers: Turso uses Elle, and S2 runs linearizability checks.

## Four DST families exist, and piton belongs in the sans-IO one

Rust DST approaches fall into four families plus whole-machine determinism. They differ mainly in when you pay: upfront in design, or later in leaks and shims.

| Approach | Tools | Strength | Weakness | Use when |
|---|---|---|---|---|
| Sans-IO state machines + custom event loop | sled recipe, Polar Signals, Firezone, hiisi | Full control of time, ordering and faults. Faults are written once at the bus, there is no async in the core, and it composes with fuzzing | Design discipline from day one; the production driver is untested glue; async dependencies are awkward | **Greenfield: piton's default** |
| Trait-abstracted runtime with a deterministic backend | commonware-runtime | Keeps async/await ergonomics without cfg magic | Every dependency must go through the runtime traits | New async code that cannot be sans-IO |
| Runtime replacement | madsim (`--cfg madsim`, shims for tonic/etcd/kafka/S3) ([README](https://github.com/madsim-rs/madsim)); turmoil + current-thread tokio ([turmoil](https://github.com/tokio-rs/turmoil)) | Retrofits onto existing tokio services | Leaks wherever dependencies bypass the runtime; patched forks to maintain; turmoil calls itself experimental | Existing async services (RisingWave, S2) |
| libc interception | mad-turmoil, madsim internals, Turso unreliable-libc | Catches HashMap seeds and `clock_gettime` in code you don't control | Platform-specific and fragile | Plugging leaks left by runtime replacement |
| Thread schedulers | loom (exhaustive), shuttle (randomized, PCT, unsound but scales) ([shuttle](https://github.com/awslabs/shuttle)) | Memory-model and lock-order bugs | Not for distributed systems or IO | Lock-free structures inside the IO shell |
| Hypervisor | Antithesis + `antithesis_sdk` ([docs](https://antithesis.com/docs/reference/sdk/rust/)) | No code changes; covers C dependencies | Commercial; you still write workloads | Whole-product system tests later |

Polar Signals considered madsim and called it "probably a good choice" for existing codebases. They chose state machines because they were writing a new database ([Polar Signals](https://blog.polarsignals.com/blog/posts/2025/07/08/dst-rust)). piton is in the same position, so the newer DST crates (moonpool, simulacra, foundationdb-simulation, refault) are optional reading. Moonpool calls itself hobby-grade, and the notes do not compare these crates' maturity ([lib.rs moonpool](https://lib.rs/crates/moonpool)).

### Testing tools: pick by what the oracle is

The testing toolbox is layered, and a pure core makes every layer cheaper, because the driver calls `step(input) -> outputs` directly and nothing needs mocking.

Two piton-specific points follow from the notes. First, both S2 and Firezone use `debug_assert!` for invariant checks, and Firezone uses debug assertions as fuzzer targets ([Firezone 2026](https://www.firezone.dev/blog/finding-bugs-you-didnt-think-to-test-for)). piton bans `debug_assert!`, so invariants should be plain `assert!` or sit behind a sim-only feature. Second, piton already bans hash-ordered collections, which closes the `RandomState` leak S2 had to fix with libc overrides ([S2](https://s2.dev/blog/dst)). The researchers also suggest, as their own inference rather than a sourced recommendation, using `clippy.toml` `disallowed-methods`/`disallowed-types` in core crates to ban `std::time::{Instant, SystemTime}`, `std::thread::spawn`, `rand::thread_rng` and `spawn_blocking`.

## Conclusion

The literature has shifted in emphasis. Python's original sans-IO argument was reuse across sync and async callers. The 2024–2026 Rust argument is testability: a pure core turns DST, model-based testing and fuzzing into one harness rather than three projects. Firezone's 2026 results are the clearest evidence that this compounding is real. The open risks are not in the core. They are in the shell and in the model. Polar Signals and Firezone both report logic drifting into untested drivers, and reference models that are themselves wrong. piton should therefore treat the IO shell's thinness as an invariant to enforce, not a goal to aim for, and keep its reference models small enough (ShardStore's ~1% rule) that a mismatch is more likely a code bug than a model bug.

A practical sequence follows. Fix the `handle(input, now)` / `poll_output()` contract and the single-seed harness before writing much protocol logic. Add proptest-state-machine conformance per component. Make the harness `arbitrary`-driven so the same code can go under cargo-fuzz nightly. Add a run-twice determinism check in `just ci`. Settle the replacement for `debug_assert!` early, because every exemplar harness depends on dense invariant checks.
