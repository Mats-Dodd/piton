# Check the real core, validate the shell

piton should run three layers of verification over one shared vocabulary of environment actions. First, a Stateright `Model` wraps the real `Session` together with a small hand-written environment model (`Env`) and checks safety properties exhaustively at small bounds. Second, the same action alphabet drives seeded random walks over the core, a cheap sans-IO DST that needs no tokio. Third, an S2-style turmoil simulation of `piton-server` emits a newline-delimited JSON trace at the core boundary, and a validator replays that trace through the Stateright model. The coordinator's plan to "do A, then B" is right, with one correction. Replaying a DST trace through option A (the real `Session` inside `next_state`) is tautological for the core's logic, but it is not meaningless. It checks that the shell actually honours the environment contract the model checker assumed: one append in flight, completions only for dispatched effects, and crashes that lose only unacknowledged writes. It also checks that the core is deterministic across versions. Option B, a separate abstract model of the effect lifecycle, should stay narrow, at roughly ShardStore's 1%-of-implementation scale. It should be added when a real need appears, and it is better checked as an exhaustive refinement inside the checker than mainly through traces. The tools fit this plan but have hard limits. Stateright has had no commit since its 0.31.0 release on 2025-07-27, offers no trace-validation feature, has no partial-order reduction, and its `eventually` checker is unsound on cycles. turmoil requires `--cfg tokio_unstable`, only covers tokio hosts, and cannot simulate Cloudflare Durable Objects. No public project replays DST traces into Stateright, so piton would be the first. Its single-threaded, deterministic, log-folding core is the most favourable case the trace-validation literature describes.

## Published trace validation succeeded when the model matched implementation steps

Every serious trace-validation effort found real discrepancies. What separated success from failure was granularity and observability, not tooling. **CCF bound a TLA+ spec to its C++ consensus with about 15 log statements at side-effect-free linearization points, driven by a deterministic scenario driver with one global clock, and found 6 subtle bugs before production**. Its trace validation caught a serious commit-advance safety bug that exhaustive model checking had missed. DFS validated a trace in under a second, against about an hour for BFS ([Howard et al., NSDI 2025](https://arxiv.org/html/2406.17455)). The cost was real: about 2 engineer-months, 107 changes to the consensus spec and 88 commits to the trace spec ([CCF](https://arxiv.org/html/2406.17455)). MongoDB's 2020 attempt failed instead. Its spec was too abstract, so **the first violation came 4 steps into a 2,683-step trace**, 252 of 345 spec lines had to change, and capturing consistent snapshots of multithreaded state took about a month for 7 transitions. The project was abandoned after 10 weeks. Meanwhile, model-generated tests for Realm Sync reached **100% branch coverage against 21% for handwritten tests** ([Davis et al., PVLDB 2020](https://arxiv.org/html/2006.00915v1)). Davis's 2025 retrospective gives the lesson directly: write the spec "with trace-checking in mind" and model easily observed events rather than internal snapshots ([MongoDB blog](https://www.mongodb.com/company/blog/engineering/conformance-checking-at-mongodb-testing-our-code-matches-our-tla-specs)).

The theory explains why. Trace validation is a constrained search for a model behaviour whose projection equals the trace. Logging events, their arguments and the resulting state keeps the search small. **Logging only variables, or only event names, "quickly leads to state-space explosion"**, and logging too little "may even lead to erroneous traces being accepted" ([Cirstea et al., 2024](https://arxiv.org/html/2404.16075v2)). Mismatched granularity forces stuttering steps and action composition. TLC gained an A∘B operator specifically for implementation steps that cover several spec steps ([Cirstea et al.](https://arxiv.org/html/2404.16075v2)). etcd's raft adopted CCF's approach in 2024 with a no-op tracer for normal builds. Reviewers then found that per-node traces lose cross-node interleavings ([etcd PR #113](https://github.com/etcd-io/raft/pull/113)).

piton has already designed away MongoDB's failure modes. Its core is single-threaded, so there are no snapshots to coordinate. Time arrives as the `now` argument, so there is no clock merging. The core's state is a fold of a durable log, so the abstraction function can be computed from the log rather than from internal fields. The conclusion for the trace boundary is that **the model's step must be exactly one `Session::handle(now, Input)` followed by draining `poll_submission`/`poll_publish`**. With that granularity there are no composition or stutter rules, and a fully logged trace turns validation into a deterministic fold with no search. This supports the coordinator's view that the trace boundary should be the core interface. It needs one extension. Crash, `from_log` recovery, indeterminate append outcomes and fencing races never pass through `handle`, but the model needs them, so the trace must record them as environment events.

## Stateright checks real Rust code but leaves trace replay to you

Stateright's core API is small: `Model` with `init_states`, `actions` and `next_state`; `Property` as a plain `fn` pointer with `always`, `sometimes` or `eventually` semantics; and a `CheckerBuilder` that spawns BFS, DFS, on-demand, simulation or Explorer runs ([src/lib.rs](https://github.com/stateright/stateright/blob/master/src/lib.rs); [src/checker.rs](https://github.com/stateright/stateright/blob/master/src/checker.rs)). Its pitch is that "the code you check is the code you run": the book says the model and implementation "are encouraged to share code" ([Comparison with TLA+](https://www.stateright.rs/comparison-with-tlaplus.html)). Wrapping piton's `Session` inside `next_state` is therefore the intended use. The precedent is Liangrun Da's check of the real Raft Lite implementation, which became the Raft example in 0.31.0 ([Kleppmann](https://nondeterministic.computer/@martin/112005567974060209); [CHANGES.md](https://github.com/stateright/stateright/blob/master/CHANGES.md)).

The constraints that matter for piton come from the source:

| Limit | Evidence | Consequence for piton |
|---|---|---|
| State must be `Clone + Hash + PartialEq + Send + Sync` (`Debug` for Explorer) | Checker bounds ([checker.rs](https://github.com/stateright/stateright/blob/master/src/checker.rs)) | `Session` and its contents derive these in `no_std`. Do not put `Box<dyn>` or closures in `Session`. `BTreeMap`/`Vec` already fit piton's lint ban on hash-ordered collections. |
| `actions()` order must be deterministic and is called twice per state | Docs and `path.rs` panic message warn about `HashMap` iteration ([path.rs](https://github.com/stateright/stateright/blob/master/src/checker/path.rs)) | Generate actions from `BTreeMap` order only. Keep `actions()` pure and cheap. |
| `next_state` returning `None` means a disabled action, not a self-loop | `if next_state.is_none() { continue; }` in BFS ([bfs.rs](https://github.com/stateright/stateright/blob/master/src/checker/bfs.rs)) | Use `None` for "the environment cannot do this now". |
| `eventually` is unsound on cycles and DAG re-joins | Doc comment and the `fixme_can_miss_counterexample_when_revisiting_a_state` test ([lib.rs](https://github.com/stateright/stateright/blob/master/src/lib.rs); [checker.rs](https://github.com/stateright/stateright/blob/master/src/checker.rs)) | Write liveness as a safety check at quiescent states, for example "no dispatched effect lacks a terminal completion once the environment has nothing left to deliver". |
| Visited states are deduplicated by a 64-bit fingerprint alone | `NonZeroU64` from `ahash` with fixed seeds ([lib.rs](https://github.com/stateright/stateright/blob/master/src/lib.rs)) | A collision silently prunes a state. This is negligible at piton's scale, but it is not zero. |
| No partial-order reduction; symmetry reduction is available | "postponed until DPOR is implemented" ([bfs.rs](https://github.com/stateright/stateright/blob/master/src/checker/bfs.rs)); `symmetry_fn` ([representative.rs](https://github.com/stateright/stateright/blob/master/src/checker/representative.rs)) | With N effects in flight, completions can arrive in N! orders. Keep bounds at 2–3 concurrent effects and 1–2 crashes, and use `within_boundary` to cap log length. |
| No trace-validation API | `Path::from_actions` returns `None` on the first mismatch, without saying where or why; no issue on the subject exists ([path.rs](https://github.com/stateright/stateright/blob/master/src/checker/path.rs); [issues](https://api.github.com/repos/stateright/stateright/issues?state=all&per_page=100)) | Write a 100–200 line validator over `actions`/`next_state`/`properties`. Use `Path` only to render an accepted trace in the Explorer. |

Scale is modest but enough. The bundled examples assert between 54 and 16,668 unique states (Paxos is 16,668). The author's own two-phase-commit benchmark ran **12.3× faster than TLC at 10 resource managers** (54.7 s against 674 s), though nobody has verified that independently ([examples/paxos.rs](https://github.com/stateright/stateright/blob/master/examples/paxos.rs); [Comparison with TLA+](https://www.stateright.rs/comparison-with-tlaplus.html)). The researchers estimate that 10^4–10^6 states will check comfortably on a laptop, but that is an extrapolation and has not been measured. The actor layer (`ActorModel`, networks, UDP `spawn`) fits piton poorly, because piton is one node whose nondeterminism is the ordering of IO completions, not a network of peers. Its 0.31.0 crash-and-recover support (`Actor::Storage`, `Out::save`, `Recover`) is still worth reading as a reference for modelling `from_log` ([src/actor.rs](https://github.com/stateright/stateright/blob/master/src/actor.rs)).

### Maintenance risk is moderate, and dev-only use contains it

Stateright is MIT-licensed. Its latest release is **0.31.0, published 2025-07-27, and nothing has been committed to master since**. Releases have come about once a year since 2022, no crate version declares an MSRV, git tags stop at v0.30.1, and a clippy-fix PR for Rust 1.90 has sat open since October 2025 ([crates.io](https://crates.io/api/v1/crates/stateright/versions); [GitHub issues](https://api.github.com/repos/stateright/stateright/issues?state=all&per_page=100)). Features since 2024 have come mostly from outside contributors at universities, Microsoft and Google ([commit history](https://github.com/stateright/stateright/commits/master)). There are only 18 reverse dependencies and no confirmed production user ([crates.io reverse deps](https://crates.io/api/v1/crates/stateright/reverse_dependencies?per_page=100)). Stateright also pulls in `tiny_http`, `serde_json`, `dashmap`, `parking_lot`, `rand` and `ahash` unconditionally, and it has no cargo features to turn them off ([Cargo.toml](https://github.com/stateright/stateright/blob/master/Cargo.toml)).

That is acceptable only because none of it reaches production code. Declare `stateright = { version = "=0.31.0", default-features = false }` once in the root `[workspace.dependencies]`. The `default-features = false` does nothing here, but it keeps the house rule. Pin the version exactly, and use it only from test code. piton depends on a small, stable part of Stateright: `Model`, `Property`, `CheckerBuilder` and `Path`. If upstream stalls for good, piton can vendor it, or replace it with a single-threaded BFS of about 300 lines over the same `Model`-shaped trait. Because the model is written against that trait shape, this is a migration, not a rewrite.

## Option A first, with the environment model as the real specification

Under option A, the model state is `(Session, Env)`. `Env` holds the durable log (`Vec<Record>`), the single unacknowledged append, the dispatched-but-uncompleted effects, the crash count and a logical clock. The actions are environment events: `AckAppend`, `RejectAppend`, `AppendIndeterminate`, `Complete{id, outcome}`, `Cancel`, `Input(k)` over a tiny alphabet, `Tick`, `Crash` and `Recover`. `next_state` clones the state and feeds the event to `Session::handle`. It then drains `poll_submission()` into `Env`, failing the step if a second `Append` appears while one is in flight. `Crash` keeps only the durable log, and `Recover` replaces the session with `Session::from_log(log)`. The `always` properties then check piton's contract directly on real code. This design is the researchers' own proposal; no published example exists:

- write-ahead: every `Dispatch(effect)` has its intent record durable at offset `EffectId`;
- exactly one terminal completion per effect;
- `Cancel` only targets live effects;
- `Unsafe` effects are never re-dispatched after recovery, and `Keyed` effects carry the same key on re-dispatch;
- `from_log(durable_log)` equals the live session's observable state at every point;
- at quiescence, no effect is pending.

Each of these is a `fn(&Model, &State) -> bool`, so bounds and parameters live in the model struct. A counterexample is a shortest action sequence, and `Checker::assert_discovery` can replay it as a permanent regression test ([checker.rs](https://github.com/stateright/stateright/blob/master/src/checker.rs)).

This is where the coordinator's framing needs correcting. Under A, `Env` is not "the implementation". It is a hand-written specification of what the shell, the LogStore and the ToolHost are allowed to do. Every exhaustive result Stateright reports is conditional on that specification. Suppose the real shell can deliver a completion after a `Cancel` has already produced a terminal record, or the real LogStore lands an append after reporting a timeout. If `Env` forbids these, the model checker never explores them. S2 hit exactly this class of problem. Its first linearizability model produced false violations because a client continued after an indefinite failure, and the fix was to model "may land later" explicitly ([S2 linearizability post](https://s2.dev/blog/linearizability)). Replaying DST traces through model A therefore answers a meaningful question: **did the shell, under faults, only ever produce environment events that `Env` admits?** It also catches core nondeterminism and version skew, because the replayed `Session` must emit the same submissions the shell observed. The only tautological part is re-checking the core's logic against itself.

Option B, a separate abstract effect-lifecycle model linked by an abstraction function α, adds an oracle that does not share the core's bugs. It also allows larger bounds, because it drops payloads, offsets and timers. Prior art cuts both ways. ShardStore's executable Rust reference models were about **1% of implementation size** and prevented 16 issues from reaching production ([Bornholt et al., SOSP 2021](https://jamesbornholt.com/papers/shardstore-sosp21.pdf)). MongoDB's over-abstract spec diverged within 4 steps ([Davis et al.](https://arxiv.org/html/2006.00915v1)). Every additional spec also has a high marginal cost to keep aligned ([MongoDB blog](https://www.mongodb.com/company/blog/engineering/conformance-checking-at-mongodb-testing-our-code-matches-our-tla-specs)). The practical answer is to build B only when A's properties start to restate the core's own logic. That point comes when "which submissions should follow this input" can no longer be written as a short invariant. When B is built, check refinement inside the A checker first. Add a `refines: bool` field that `next_state` sets by testing whether α(s′) equals α(s) (a stutter) or is a successor of α(s) under the abstract model, and add the property `always refines`. Stateright's properties see only the current state, so this flag is the standard way to express a step property. It gives exhaustive refinement at A's bounds for free. DST traces then validate against B too, which pays off for traces from hosts the checker never runs, such as Durable Objects and production input journals. Model-to-implementation test generation from B (`Path::into_actions()` driving the real core, as quint-connect does from Quint) adds little while A already explores the real core exhaustively. It becomes useful only if B's bounds reach deeper than A's ([quint-connect](https://quint.sh/posts/quint_connect)).

## S2's harness transfers almost verbatim, minus its assertions and channels

S2's DST recipe is public, small, and proven in CI. Its blog names four sources of nondeterminism to control: execution, entropy, time and I/O. It runs on every PR plus "thousands of nightly trials", and found 17 notable bugs ([S2 DST post](https://s2.dev/blog/dst)). The open-source harness is **about 1,200 lines in `s2/sim/`**. It is a separate cargo workspace "to isolate its patched dependencies", using turmoil 0.7.2, mad-turmoil 0.2.1 and a patched `getrandom`, because upstream getrandom 0.2 issues a raw syscall that bypasses libc interposition. Setup is `SimClocksGuard::init()`, `set_rng(seed)` and `fastrand::seed(seed)`, then a turmoil `Builder` with a seed, a 4-hour simulated duration, 2–30 ms latency and an optional `fail_rate`. Dependencies such as S3 run as in-memory emulators on their own turmoil hosts. A `meta` subcommand runs the same seed twice at `RUST_LOG=trace` and kills both runs at the first differing line ([s2/sim](https://github.com/s2-streamstore/s2/tree/main/sim); [sim/Cargo.toml](https://github.com/s2-streamstore/s2/blob/main/sim/Cargo.toml)). Public CI uses only about five seeds plus three meta runs, on `ubuntu-24.04-arm`. The arm runner is there because a dependency's pre-main TSC calibration spins forever under the interposed clock on x86_64 ([s2 ci.yml](https://github.com/s2-streamstore/s2/blob/main/.github/workflows/ci.yml)).

turmoil 0.7.2 runs each host on a `current_thread` runtime with `start_paused(true)` on a `LocalSet`. It seeds tokio's RNG, which drives `select!` branch order, only under `cfg(tokio_unstable)`. `Sim::crash` drops a host's runtime, and `bounce` restarts it from its factory closure ([rt.rs](https://github.com/tokio-rs/turmoil/blob/main/crates/turmoil/src/rt.rs); [sim.rs](https://github.com/tokio-rs/turmoil/blob/main/crates/turmoil/src/sim.rs)). tokio says seed-determinism also requires fixed tokio, dependency and rustc versions ([tokio Builder](https://docs.rs/tokio/latest/tokio/runtime/struct.Builder.html)). devenv's pinned toolchain and the lockfile already provide that. madsim offers more complete determinism, including thread-spawn detection and a built-in `check_determinism`. The price is replacing tokio and patching several crates ([madsim](https://github.com/madsim-rs/madsim)). Since piton is hyper/WebSocket-based and uses `#[async_trait]`, turmoil plus mad-turmoil is the lower-friction choice.

Mapped onto piton, the harness is a separate `sim/` workspace. It contains:

- **The shell host.** `sim.host("shell", || shell_main(cfg))`, built from the real `piton-server` pump.
- **The LogStore host.** A `MemLogStore` on its own host behind a small RPC, following Materialize's turmoil `Consensus`, which returns `CaSResult` with determinate and indeterminate errors ([materialize persist/turmoil.rs](https://github.com/MaterializeInc/materialize/blob/main/src/persist/src/turmoil.rs)). Running it on its own host lets turmoil crash the shell independently of it.
- **LogStore faults.** Definite reject, applied-but-response-lost, timeout-not-landed, delayed apply after the client gave up, and a stale fence token racing a new writer.
- **The model provider host.** A seeded fake streaming provider served by axum, reached through an injected hyper connector, as S2 injects `S2::new_with_connector` ([s2 sim/src/net.rs](https://github.com/s2-streamstore/s2/blob/main/sim/src/net.rs)). It covers mid-stream disconnects, stalls, 429/5xx responses and malformed chunks.
- **ToolHost faults.** An in-process fault-injecting decorator in the style of opbox's `FaultInjectingFileIO`, covering error, timeout, duplicate completion and late completion after cancel ([opbox](https://github.com/s2-streamstore/opbox/blob/main/sim/src/fault_injecting_file_io.rs)).
- **Clients.** `sim.client` workloads over Attach/Submit/Cancel, with partitions for reconnect.

Four adaptations are mandatory. S2 relies on `debug_assert!` for expensive checks ([S2 DST post](https://s2.dev/blog/dst)), and piton bans it, so run the sim under a `[profile.sim]` with overflow checks and use plain `assert!`. History sinks must be bounded or a `Vec` drained after `sim.run()`, never unbounded channels. mad-turmoil is `#[no_mangle]` libc interposition that its README says to use "only for simulation binaries" ([mad-turmoil](https://github.com/s2-streamstore/mad-turmoil)), so it belongs only in the sim binary, under an `#[expect(unsafe_code, reason = "...")]`. Finally, the HTTP provider must accept an injected connector, because reqwest's built-in connector cannot run over turmoil.

Three gaps remain. WebSocket over `turmoil::net::TcpStream` should work through `tokio-tungstenite::client_async`, but nobody has shown it. turmoil cannot run in a Durable Object, because it depends on tokio and libc interposition. Whether std's `HashMap` `RandomState` goes through the interposed libc symbols is also unverified, though piton's ban on hash-ordered collections removes the first-party risk.

The sans-IO design makes most of this machinery less central than it was for S2. S2 retrofitted DST onto an existing async server. piton's interesting logic lives in a core that can be driven without tokio. The cheapest and deepest DST for piton is therefore a seeded random walk over the same `Env` action alphabet used by the Stateright model: thousands of seeds per second, no `tokio_unstable`, and running in `just ci` alongside unit tests. The turmoil sim then has a narrower job. It tests what the core cannot see: pump scheduling, connection lifecycle, LogStore fencing over a lossy network, journal durability across `crash`/`bounce`, and provider codec streaming. This split also follows the earlier warning from Polar Signals that logic drifts into the untested driver ([Polar Signals](https://blog.polarsignals.com/blog/posts/2025/07/08/dst-rust)). The turmoil sim exists to keep that driver honest. It is not the primary test of the core.

## One journal format serves production recovery, DST and replay

The trace should extend the input journal that piton already writes, rather than introduce a second format. A production journal of `(now, Input)` is already a replayable core trace. DST adds observed outputs and environment events in simulator order. That gives one global order, which avoids the per-node interleaving loss etcd's reviewers flagged ([etcd PR #113](https://github.com/etcd-io/raft/pull/113)). Following CCF, record constant-size summaries rather than contents, such as log lengths and hashes ([CCF](https://arxiv.org/html/2406.17455)). Following S2, chain payload hashes with xxh3 so that a lost or reordered record anywhere fails the check ([s2-verification](https://github.com/s2-streamstore/s2-verification)). One ndjson line per step:

```text
{"seq":412,"sim_ms":91234,"host":"shell","session":"s1","ev":"handle",
 "now":91230,"input":{"AppendAck":{"offset":17}},
 "out":[{"Dispatch":{"id":17,"policy":"Keyed"}}],"pub":1,
 "proj":{"durable_len":18,"in_flight_append":null,"open":[17],"terminal":[3,9],"log_hash":"9f2c…"}}
{"seq":413,"sim_ms":91240,"host":"logstore","ev":"env","env":{"AppendIndeterminate":{"expected":18,"landed":true}}}
{"seq":414,"sim_ms":91300,"host":"shell","ev":"env","env":"Crash"}
{"seq":415,"sim_ms":91500,"host":"shell","ev":"env","env":"Recover"}
```

`proj` is α computed from the durable log, so it does not depend on implementation internals and B can reuse it. The core's `Input` and `Submission` types derive `serde` behind a `trace` feature, with the workspace `serde` declared `default-features = false` and the `derive` and `alloc` features enabled. This keeps the core `no_std` and costs nothing in builds without the feature, the same pattern as etcd's `state_trace_nop.go` ([etcd PR #113](https://github.com/etcd-io/raft/pull/113)).

The validator keeps a frontier of model states, normally of size 1. For each line it maps the event to a model action, checks that the action is in `model.actions(&s)`, applies `next_state`, and asserts three things: that the emitted submissions equal `out`, that α equals `proj`, and that every `always` property holds. On failure it reports the step number, the last good state and a structural diff, which is quint-connect's ergonomic lesson ([Quint blog](https://quint.sh/posts/quint_connect)). The frontier only grows past 1 where the trace deliberately omits something, such as a `landed` flag the shell cannot observe. In that case the frontier branches over the possibilities, as Cirstea et al. do for unlogged arguments ([Cirstea et al.](https://arxiv.org/html/2404.16075v2)). Aggregated over the corpus, two more checks come from the same pass. Model actions and α-states that no trace ever reaches show DST generator blind spots. Rejected steps show drift, and CCF found these were mostly spec bugs at first, so budget for that ([CCF](https://arxiv.org/html/2406.17455)).

Crate layout should follow CLAUDE.md's rule that a crate marks a real boundary. The specification is one: `crates/piton-model` (`publish = false`) holds `Env`, the action alphabet, α, the properties, the Stateright `Model` impl, the trace validator and the core random walk. It depends on `piton-core` and Stateright. `piton-core` uses it only as a dev-dependency, and the `sim/` workspace uses it to validate its traces. Before the sim exists, the same code can live in `piton-core/tests/` and move out when a second consumer appears.

| Stage | Runs in | Contents | Budget |
|---|---|---|---|
| `just ci` (every commit and PR) | root workspace | Unit and property tests; Stateright BFS at small bounds (2 effects, 1 crash, log ≤ 8) with `assert_properties()`, single-threaded for shortest counterexamples; core random walk over about 1,000 seeds; replay of checked-in regression traces and `assert_discovery` fixtures | Under 2 minutes |
| `just sim` (called by `just ci`, same recipe in GitHub Actions) | `sim/` workspace, `RUSTFLAGS=--cfg tokio_unstable`, arm64 runner | Meta determinism test on 2–3 seeds at `RUST_LOG=trace`; about 5 fault seeds including a non-zero `fail_rate`; validation of every emitted trace; upload of traces on failure | Under 15 minutes, matching S2's 30-minute ceiling ([s2 ci.yml](https://github.com/s2-streamstore/s2/blob/main/.github/workflows/ci.yml)) |
| Nightly | both | Stateright BFS or DFS at larger bounds plus `spawn_simulation`; thousands of sim seeds in parallel; coverage report of the model reached by traces; refinement against B once B exists | Hours |

Having `just ci` call `just sim` keeps local and CI validation on one path, as CLAUDE.md requires, despite the separate `cfg`. Any failing seed becomes a checked-in trace file plus a `Path`-based regression test, because seeds stop reproducing once the code changes ([Eaton](https://notes.eatonphil.com/2024-08-20-deterministic-simulation-testing.html)).

## Conclusion

The most useful change of view is about what the model checker actually verifies. With the real core inside `next_state`, piton's exhaustive guarantees are only as true as `Env`, the hand-written model of the shell and storage. That moves the weight of trace validation from "does the core match a spec" to "does the shell keep the promises the checker assumed". It also means piton's first trace-validation bugs will most likely be found in the LogStore's indeterminate-outcome handling and in cancel/complete races, not in core logic. Building that `Env` carefully, with S2's "may land later" lesson built in from the start, is worth more than an early option B.

The second implication is that piton's architecture lets one artifact do three jobs. The extended input journal is the recovery log in production, the DST trace in simulation, and the model-checking witness in replay. No published system has closed this loop with Stateright, so piton's work here is novel. The work is still mostly plumbing, not research, because the core already sits at the granularity that made CCF succeed and MongoDB fail. The real long-term risks are Stateright's dormant upstream and the hosts turmoil cannot reach, such as Durable Objects. Both are contained the same way: keep the model behind a small trait-shaped boundary, and keep every host's shell thin enough that the journal-replay check covers it.
